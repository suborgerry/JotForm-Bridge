# STAGE 5 — The Auto-Generate Renderer

> **Historical.** This stage is finished. The file records what was asked for at
> the time, not what the code does now — some of it has since been overturned by
> the `Amendment:` sections in `AGENTS.md`. Read it for the reasoning, not as an
> instruction, and never as a description of current behaviour.

Read `AGENTS.md`.

The custom template flow is already the working base of the system. AutoRenderer
is only the second way of rendering.

It has to use what already exists:

* Integration;
* the Normalized Schema;
* SubmissionValidator;
* SubmissionMapper;
* the REST endpoint;
* frontend.js.

Do not create a separate submission pipeline.

---

## 1. AutoRenderer

Create an AutoRenderer that builds a form from the Normalized Schema.

The main goal is markup that is:

* functional;
* semantic;
* accessible;
* easy to style.

Do not try to reproduce Jotform's design.

---

## 2. Supported fields

Render only the normalized types that are genuinely supported. At a minimum:

* text;
* textarea;
* email;
* phone;
* number;
* select;
* radio;
* checkbox;
* full name;
* address.

Date only if the schema and submission layers already support it correctly.

---

## 3. Semantic HTML

Use:

* `<form>`;
* `<label>`;
* `<input>`;
* `<textarea>`;
* `<select>`;
* `<fieldset>`;
* `<legend>`.

Every field gets a stable, unique HTML ID. Every label is associated with its
field. A required field carries the matching semantics. Choice groups use
`fieldset` and `legend` where that is appropriate.

---

## 4. data-jotform-field

AutoRenderer generates the same frontend contract as a custom template:

`data-jotform-field="email"`

`data-jotform-field="name.first"`

and so on.

The existing `frontend.js` therefore has to work with no AutoRenderer-specific
branches.

---

## 5. CSS hooks

Add predictable structural classes:

`.jfb-form`

`.jfb-field`

`.jfb-field--text`

`.jfb-field--email`

`.jfb-field--select`

`.jfb-field--checkbox`

`.jfb-error`

`.jfb-submit`

Do not ship heavy default CSS. Do not impose a design system.

---

## 6. Error hooks

The generated form contains the markup the existing frontend JS uses for:

* field errors;
* global form errors;
* success and error events.

Do not create a second JS implementation.

---

## 7. Unsupported fields

A required unsupported field: AutoRenderer must not produce a form that cannot
possibly submit correctly. Show the administrator a blocking diagnostic, and let
the frontend fail safely.

Optional unsupported fields may be skipped, but only with an explicit warning or
diagnostic.

---

## 8. Admin integration

Where Rendering Mode = `auto`, the template select is irrelevant and should be
disabled or hidden accordingly.

The Integration compatibility UI shows:

* schema ready;
* unsupported required fields;
* auto renderer readiness.

An administrator can switch:

Custom → Auto

and:

Auto → Custom

without recreating the Integration.

---

## 9. Accessibility

Check at least:

* labels;
* unique IDs;
* required;
* radio group semantics;
* checkbox group semantics;
* errors with aria-live;
* keyboard accessibility;
* no JS-only labels.

---

## 10. Tests

Add render tests for:

* text;
* textarea;
* email;
* phone;
* number;
* select;
* radio;
* checkbox;
* full name;
* address;
* required;
* required but unsupported.

Assert the correct field attributes, not merely that some string is present.

---

## 11. MCP verification

Playwright:

1. Set an Integration to Auto.
2. Open the frontend.
3. Check the generated markup.
4. Check keyboard and basic accessibility behaviour.
5. Submit an empty form.
6. Check the errors.
7. Fill the form in.
8. Submit.
9. Check the success state.

Where a test Jotform form is available, check a real end-to-end submission.

WordPress Playground:

* switching renderers;
* the shortcode and the helper;
* no fatal errors;
* no unnecessary API requests.

---

## Acceptance criteria

One Integration can switch between:

Custom Template
and
Auto Generate

with the submission pipeline staying the same.

AutoRenderer uses the Normalized Schema and nothing else.

Afterwards state:

* which normalized types AutoRenderer supports;
* which are unsupported;
* the accessibility checks;
* the tests;
* the MCP verification.

Do not move on to the next stage on your own.
