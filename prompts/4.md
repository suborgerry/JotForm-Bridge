# ЭТАП 4 — Custom Template Rendering и полный Submission Pipeline

Прочитай `AGENTS.md`.

Изучи реализацию предыдущих этапов.

На этом этапе реализуй первый рабочий end-to-end flow:

Custom PHP Template
→ Browser
→ WordPress REST API
→ Validation
→ Mapping
→ Jotform REST API

Не реализовывай AutoRenderer.

---

## 1. CustomTemplateRenderer

Создай renderer зарегистрированных PHP templates.

Можно include/render только template из TemplateRegistry.

Arbitrary filesystem paths запрещены.

Template context должен содержать только необходимые значения, например:

* Integration;
* Normalized Schema;
* REST endpoint.

Не передавать API key.

Не заставлять template знать Jotform Form ID/qid.

---

## 2. Template Form Contract

Custom template должен использовать:

```html
<form
    data-jotform-bridge
    data-jotform-integration="contact"
>
```

Fields:

```html
<input data-jotform-field="email">
```

Composite:

```html
<input data-jotform-field="name.first">
<input data-jotform-field="name.last">
```

Ошибки:

```html
<div data-jotform-errors aria-live="polite"></div>
```

Допускаются дополнительные theme-specific classes/markup.

---

## 3. Public PHP API

Добавь:

```php
jotform_form('contact')
```

Предпочтительно функция возвращает HTML.

Использование:

```php
echo jotform_form('contact');
```

Если Integration:

* отсутствует;
* disabled;
* invalid;
* template missing;

не должно быть fatal error.

Возвращай безопасное пустое/diagnostic behavior согласно environment/debug mode.

---

## 4. Shortcode

Добавь:

```text
[jotform_form id="contact"]
```

PHP helper и shortcode используют один FormRenderer.

Не дублировать business logic.

---

## 5. Frontend assets

Создай готовый vanilla JS asset.

Никакого jQuery.

Не нужен Node/build step для production.

Не добавлять тяжелые frameworks.

По возможности enqueue script только там, где Jotform Bridge form действительно rendered.

---

## 6. Frontend serializer

JavaScript должен собирать semantic fields по:

`data-jotform-field`

Поддержать:

* text;
* email;
* textarea;
* number;
* select;
* radio;
* checkbox;
* multiple checkbox;
* composite fields.

Request concept:

```json
{
    "fields": {
        "name.first": "John",
        "name.last": "Smith",
        "email": "john@example.com"
    }
}
```

Не отправлять:

* Jotform Form ID;
* qid;
* API key.

---

## 7. Frontend UX

При submit:

* `preventDefault`;
* block double submission;
* disable submit button;
* clear previous errors;
* send request;
* process response;
* restore state when required.

Dispatch events:

`jotformbridge:before-submit`

`jotformbridge:success`

`jotformbridge:error`

Events должны содержать полезный, но безопасный detail.

Не навязывать:

* popup;
* redirect;
* animation.

---

## 8. REST Route

Создай:

`POST /wp-json/jotform-bridge/v1/submit/{integration}`

Использовать standard WP REST API.

Public endpoint может иметь public permission callback, но security обеспечивается полноценной validation pipeline.

Integration slug из URL — только lookup key.

Backend самостоятельно определяет Jotform Form ID.

---

## 9. SubmissionValidator

Создай отдельный service.

Проверять:

* Integration существует;
* Integration Active;
* schema существует;
* semantic field разрешен;
* required fields;
* required composite children;
* scalar vs array;
* email;
* number;
* allowed select options;
* allowed radio options;
* allowed checkbox options;
* string length sanity;
* request size sanity.

Sanitize соответственно type.

Unknown fields не принимать молча.

Не использовать client-provided field type.

---

## 10. SubmissionMapper

Создай отдельный service:

Normalized semantic values
→ exact Jotform submission payload.

Это один из критичных компонентов.

Перед реализацией ОБЯЗАТЕЛЬНО проверь актуальную официальную документацию Jotform API.

Особенно проверить:

* submission endpoint;
* encoding/content type;
* question ID format;
* composite fields;
* fullname;
* address;
* checkbox;
* radio;
* dropdown;
* phone.

Не угадывай payload.

REST Controller не должен содержать mapping logic.

---

## 11. JotformClient submission

Добавь только необходимый method для отправки submission.

Используй существующую HTTP/error infrastructure.

Не выводить upstream sensitive response на frontend.

---

## 12. Spam extension point

На этом этапе не обязательно интегрировать captcha.

Но до реальной отправки в Jotform должен существовать extension point:

например:

`jotform_bridge_spam_check`

или небольшая abstraction.

Future Turnstile integration не должна требовать переписывать SubmissionController.

---

## 13. Response Contract

Validation:

HTTP 422

```json
{
    "success": false,
    "message": "Validation failed.",
    "errors": {
        "email": "Invalid email."
    }
}
```

Success:

```json
{
    "success": true,
    "message": "Form submitted successfully."
}
```

Unknown integration:

appropriate 404.

Disabled integration:

appropriate safe 4xx.

Jotform upstream error:

safe 5xx.

Не выдавать:

* stack traces;
* API key;
* authorization headers;
* filesystem paths;
* raw Jotform internal details.

---

## 14. Live Submission Safety

НЕ использовать произвольную production Jotform form для тестов.

Live write допустим только для явно test/development form.

Если такой form нет:

* mock Jotform upstream;
* протестировать mapper fixtures;
* протестировать REST end-to-end до upstream boundary;
* явно указать, что live Jotform submission не выполнялся.

Не создавай тестовый мусор в production account без разрешения.

---

## 15. Tests

Обязательно:

* unknown integration;
* inactive integration;
* missing required;
* invalid email;
* unknown semantic field;
* number;
* select invalid option;
* radio invalid option;
* checkbox valid/invalid;
* composite required field;
* mapper text;
* mapper email;
* mapper name;
* mapper address;
* upstream failure;
* successful mocked submission.

---

## 16. MCP Verification

WordPress Playground:

* PHP helper;
* shortcode;
* template rendering;
* REST route;
* validation;
* server-side mapping.

Playwright:

1. Открыть test page.
2. Убедиться, что custom markup rendered.
3. Submit empty form.
4. Проверить errors.
5. Заполнить fields.
6. Submit.
7. Проверить disabled/loading behavior.
8. Проверить отсутствие двойной отправки.
9. Проверить success/error event/state.

Jotform MCP:

Если есть development/test form:

* отправить через настоящий browser flow;
* затем read-only проверить появление submission;
* сравнить значения.

---

## Acceptance Criteria

Custom Template end-to-end flow должен работать без AutoRenderer.

Theme developer должен иметь возможность:

1. создать `/forms/contact.php`;
2. зарегистрировать Integration через Admin;
3. добавить:

```php
echo jotform_form('contact');
```

4. увидеть свой HTML;
5. отправить форму;
6. получить server validation;
7. submission должен быть mapped по schema;
8. Jotform API key не должен появляться в browser.

В конце предоставь:

* request flow;
* mapper architecture;
* реальные поддерживаемые field mappings;
* tests;
* Playwright results;
* live Jotform verification, если выполнялась;
* непроверенные части.

Не реализовывай AutoRenderer самостоятельно.
