# STAGE 4 — Custom Template Rendering and the Full Submission Pipeline

> **Historical.** This stage is finished. The file records what was asked for at
> the time, not what the code does now — some of it has since been overturned by
> the `Amendment:` sections in `AGENTS.md`. Read it for the reasoning, not as an
> instruction, and never as a description of current behaviour.

Read `AGENTS.md`.

Study the implementation of the previous stages.

This stage builds the first working end-to-end flow:

Custom PHP Template
→ Browser
→ WordPress REST API
→ Validation
→ Mapping
→ Jotform REST API

Do not implement AutoRenderer.

---

## 1. CustomTemplateRenderer

Create a renderer for registered PHP templates.

Only a template from the TemplateRegistry may be included or rendered. Arbitrary
filesystem paths are forbidden.

The template context carries only what it needs, for example:

* the Integration;
* the Normalized Schema;
* the REST endpoint.

Do not pass the API key. Do not make the template know a Jotform Form ID or a
qid.

---

## 2. The template form contract

A custom template uses:

```html
<form
    data-jotform-bridge
    data-jotform-integration="contact"
>
```

Fields:

```html
<input data-jotform-field="email">
```

Composite:

```html
<input data-jotform-field="name.first">
<input data-jotform-field="name.last">
```

Errors:

```html
<div data-jotform-errors aria-live="polite"></div>
```

Additional theme-specific classes and markup are allowed.

---

## 3. The public PHP API

Add:

```php
jotform_form('contact')
```

It returns HTML:

```php
echo jotform_form('contact');
```

If the Integration is:

* missing;
* disabled;
* invalid;
* missing its template;

there must be no fatal error. Return safe empty or diagnostic behaviour
depending on the environment and debug mode.

> Superseded: the helper is called `jotform_bridge_render()`.

---

## 4. Shortcode

Add:

```text
[jotform_form id="contact"]
```

The PHP helper and the shortcode use the same FormRenderer. Do not duplicate the
business logic.

---

## 5. Frontend assets

Create a finished vanilla JS asset. No jQuery. No Node or build step for
production. No heavy frameworks.

Where possible, enqueue the script only where a Jotform Bridge form is actually
rendered.

---

## 6. The frontend serializer

The JavaScript collects semantic fields by:

`data-jotform-field`

Support:

* text;
* email;
* textarea;
* number;
* select;
* radio;
* checkbox;
* multiple checkboxes;
* composite fields.

The request, conceptually:

```json
{
    "fields": {
        "name.first": "John",
        "name.last": "Smith",
        "email": "john@example.com"
    }
}
```

Do not send:

* the Jotform Form ID;
* a qid;
* the API key.

---

## 7. Frontend UX

On submit:

* `preventDefault`;
* block a double submission;
* disable the submit button;
* clear the previous errors;
* send the request;
* process the response;
* restore the state where required.

Dispatch:

`jotformbridge:before-submit`

`jotformbridge:success`

`jotformbridge:error`

The events carry useful but safe detail.

Do not impose:

* a popup;
* a redirect;
* an animation.

---

## 8. The REST route

Create:

`POST /wp-json/jotform-bridge/v1/submit/{integration}`

Use the standard WP REST API. A public endpoint may have a public permission
callback; the security comes from a full validation pipeline.

The integration slug in the URL is a lookup key and nothing more. The backend
resolves the Jotform Form ID itself.

---

## 9. SubmissionValidator

Create a separate service. It checks:

* the Integration exists;
* the Integration is active;
* a schema exists;
* the semantic field is allowed;
* required fields;
* required composite children;
* scalar vs array;
* email;
* number;
* allowed select options;
* allowed radio options;
* allowed checkbox options;
* string length sanity;
* request size sanity.

Sanitize according to the type.

Do not accept unknown fields silently. Do not use a client-provided field type.

---

## 10. SubmissionMapper

Create a separate service:

normalized semantic values
→ the exact Jotform submission payload.

This is one of the critical components.

Check the current official Jotform API documentation before implementing.
Particularly:

* the submission endpoint;
* the encoding and content type;
* the question ID format;
* composite fields;
* fullname;
* address;
* checkbox;
* radio;
* dropdown;
* phone.

Do not guess the payload. The REST controller must contain no mapping logic.

---

## 11. JotformClient submission

Add only the method needed to send a submission, using the existing HTTP and
error infrastructure.

Do not surface a sensitive upstream response on the frontend.

---

## 12. The spam extension point

Integrating a captcha is not required at this stage. But an extension point has
to exist before anything is actually sent to Jotform, for example:

`jotform_bridge_spam_check`

or a small abstraction.

A future Turnstile integration must not require rewriting SubmissionController.

---

## 13. The response contract

Validation:

HTTP 422

```json
{
    "success": false,
    "message": "Validation failed.",
    "errors": {
        "email": "Invalid email."
    }
}
```

Success:

```json
{
    "success": true,
    "message": "Form submitted successfully."
}
```

An unknown integration: an appropriate 404.

A disabled integration: an appropriate, safe 4xx.

A Jotform upstream error: a safe 5xx.

Never return:

* stack traces;
* the API key;
* authorization headers;
* filesystem paths;
* raw Jotform internals.

> Superseded: every refusal that is not the visitor's own doing answers
> identically, so the endpoint cannot be asked which slugs exist. See
> `SubmissionPipeline::unavailable()`.

---

## 14. Live submission safety

Do NOT use an arbitrary production Jotform form for tests.

A live write is permitted only against an explicitly test or development form.

If no such form exists:

* mock the Jotform upstream;
* test the mapper against fixtures;
* test the REST end-to-end up to the upstream boundary;
* state plainly that no live Jotform submission was performed.

Do not leave test rubbish in a production account without permission.

---

## 15. Tests

At least:

* an unknown integration;
* an inactive integration;
* a missing required field;
* an invalid email;
* an unknown semantic field;
* number;
* an invalid select option;
* an invalid radio option;
* checkbox, valid and invalid;
* a required composite field;
* the mapper for text;
* the mapper for email;
* the mapper for name;
* the mapper for address;
* an upstream failure;
* a successful mocked submission.

---

## 16. MCP verification

WordPress Playground:

* the PHP helper;
* the shortcode;
* template rendering;
* the REST route;
* validation;
* server-side mapping.

Playwright:

1. Open a test page.
2. Confirm the custom markup rendered.
3. Submit an empty form.
4. Check the errors.
5. Fill the fields in.
6. Submit.
7. Check the disabled/loading behaviour.
8. Check that a double submission is impossible.
9. Check the success and error events and states.

Jotform MCP, where a development or test form exists:

* send through the real browser flow;
* then check read-only that the submission appeared;
* compare the values.

---

## Acceptance criteria

The custom template end-to-end flow works without AutoRenderer.

A theme developer can:

1. create `/forms/contact.php`;
2. register an Integration in the admin;
3. add:

```php
echo jotform_form('contact');
```

4. see their own HTML;
5. submit the form;
6. get server-side validation;
7. have the submission mapped by the schema;
8. never see the Jotform API key in the browser.

Afterwards provide:

* the request flow;
* the mapper architecture;
* the field mappings actually supported;
* the tests;
* the Playwright results;
* the live Jotform verification, if one was performed;
* whatever was left unverified.

Do not implement AutoRenderer on your own.
