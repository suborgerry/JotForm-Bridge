# ЭТАП 1 — Plugin Core + Jotform Connection

Прочитай `AGENTS.md` в корне проекта и следуй ему как основной спецификации.

Реализуй только первый этап Jotform Bridge.

Не реализовывай пока:

* schema normalization;
* custom templates;
* template scanner;
* frontend forms;
* REST submission;
* AutoRenderer.

Цель этого этапа — получить надежный standalone WordPress plugin core и рабочее server-side подключение к Jotform.

## Реализовать

### Plugin bootstrap

Создай корректный WordPress plugin:

`Jotform Bridge`

Минимальные требования:

* WordPress 6.4+
* PHP 8.0+

Plugin header должен содержать соответствующие `Requires at least` и `Requires PHP`.

Используй namespace:

`JotformBridge`

Раздели bootstrap и application logic.

Не помещай всю реализацию в основной plugin file.

### Расположение

Код плагина размещай в каталоге `jotform-bridge/` в корне репозитория, как описано в `AGENTS.md`.

Main plugin file: `jotform-bridge/jotform-bridge.php`

Text domain: `jotform-bridge`

Не размещай PHP-код плагина в корне репозитория.

### Autoloading

Организуй нормальный autoloading.

Composer/PSR-4 разрешен, но конечный plugin package не должен требовать выполнения `composer install` пользователем WordPress.

Не добавляй сторонних runtime dependencies без необходимости.

### Test scaffolding

Настрой тестовую инфраструктуру уже на этом этапе, чтобы Этап 2 не начинался с нее.

Создай:

* `composer.json` с dev-зависимостями `phpunit/phpunit ^9.6` и `brain/monkey ^2.6`;
* PSR-4 автозагрузку `JotformBridge\` → `jotform-bridge/src/` и `JotformBridge\Tests\` → `tests/`;
* `phpunit.xml.dist`;
* `tests/bootstrap.php`;
* базовый `tests/TestCase.php` с setUp/tearDown Brain Monkey;
* скрипт `composer test`.

Добавь минимум один осмысленный smoke-тест, чтобы suite действительно запускался и был зеленым.

Не тяни PHPUnit 10+, он требует PHP 8.1+.

Проверь, что `composer test` проходит, и приведи вывод в отчете.

### Settings

Создай:

`Jotform Bridge → Settings`

Настройки:

* API Key
* API Region/Base URL
* Debug Logging

API key priority:

1. `JOTFORM_API_KEY`
2. WordPress option

Если `JOTFORM_API_KEY` определена:

* используй constant;
* покажи administrator, что ключ задается externally;
* не показывай значение;
* не разрешай случайно его перезаписать через UI.

Для сохраненного ключа не выводи его обратно полностью.

### JotformClient

Создай отдельный `JotformClient`.

Минимальные operations:

* test connection;
* get account forms.

Используй WordPress HTTP API.

Обрабатывай:

* timeout;
* `WP_Error`;
* non-2xx;
* malformed JSON;
* API errors.

Не передавай secrets в errors/frontend.

Перед реализацией проверь актуальную официальную Jotform REST API documentation для authentication и списка forms.

Не угадывай endpoints.

### Forms cache

Добавь получение и cache списка Jotform forms.

Admin actions:

* Test Connection
* Refresh Forms

Не обращаться к Jotform на каждом admin page view, если cached list уже актуален.

Не обращаться к Jotform на frontend page requests.

### Admin feedback

Показывай понятные состояния:

* Not configured
* Connected
* Connection failed

Для forms:

* loaded;
* unavailable;
* needs refresh.

## Безопасность

Используй:

* capability `manage_options`;
* admin nonce для actions;
* sanitization;
* contextual escaping.

Не выводи API key в HTML/JS/logs.

## Verification

После реализации обязательно:

1. Активируй plugin через WordPress Playground MCP.
2. Проверь отсутствие fatal errors.
3. Проверь появление Admin menu/settings.
4. Через Playwright MCP открой Settings page.
5. Проверь UI состояния.
6. Если Jotform connection доступен безопасно — выполни read-only Test Connection и Refresh Forms.
7. Если live connection недоступен — явно сообщи это и проверь error handling через безопасный fixture/mock или invalid configuration.

Jotform MCP можно использовать для read-only сравнения списка forms, если он доступен.

Не изменяй Jotform forms.
