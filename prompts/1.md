# STAGE 1 — Plugin Core + Jotform Connection

> **Historical.** This stage is finished. The file records what was asked for at
> the time, not what the code does now — some of it has since been overturned by
> the `Amendment:` sections in `AGENTS.md`. Read it for the reasoning, not as an
> instruction, and never as a description of current behaviour.

Read `AGENTS.md` at the project root and follow it as the primary specification.

Implement only the first stage of Jotform Bridge.

Do not implement yet:

* schema normalization;
* custom templates;
* the template scanner;
* frontend forms;
* REST submission;
* AutoRenderer.

The goal of this stage is a dependable standalone WordPress plugin core and a
working server-side connection to Jotform.

## To implement

### Plugin bootstrap

Create a correct WordPress plugin:

`Jotform Bridge`

Minimum requirements:

* WordPress 6.4+
* PHP 8.0+

The plugin header must carry the matching `Requires at least` and `Requires PHP`.

Use the namespace:

`JotformBridge`

Separate the bootstrap from the application logic. Do not put the whole
implementation in the main plugin file.

### Layout

The plugin code goes in the `jotform-bridge/` directory at the repository root,
as described in `AGENTS.md`.

Main plugin file: `jotform-bridge/jotform-bridge.php`

Text domain: `jotform-bridge`

Do not put plugin PHP code at the repository root.

### Autoloading

Set up proper autoloading. Composer and PSR-4 are allowed, but the final plugin
package must not require the WordPress user to run `composer install`.

Do not add third-party runtime dependencies without a need.

### Test scaffolding

Set the test infrastructure up in this stage, so that stage 2 does not have to
begin with it.

Create:

* `composer.json` with the dev dependencies `phpunit/phpunit ^9.6` and
  `brain/monkey ^2.6`;
* PSR-4 autoloading, `JotformBridge\` → `jotform-bridge/src/` and
  `JotformBridge\Tests\` → `tests/`;
* `phpunit.xml.dist`;
* `tests/bootstrap.php`;
* a base `tests/TestCase.php` with Brain Monkey setUp/tearDown;
* a `composer test` script.

Add at least one meaningful smoke test, so the suite really runs and is green.

Do not pull in PHPUnit 10+; it requires PHP 8.1+.

Check that `composer test` passes and include the output in the report.

### Settings

Create:

`Jotform Bridge → Settings`

Settings:

* API Key
* API Region / Base URL
* Debug Logging

API key priority:

1. `JOTFORM_API_KEY`
2. a WordPress option

If `JOTFORM_API_KEY` is defined:

* use the constant;
* show the administrator that the key is set externally;
* do not show its value;
* do not allow it to be overwritten accidentally through the UI.

Never print a stored key back in full.

> Superseded: the option was later removed as a key source entirely. See "The
> API key" in `AGENTS.md`.

### JotformClient

Create a dedicated `JotformClient`.

Minimum operations:

* test connection;
* get account forms.

Use the WordPress HTTP API, and handle:

* timeouts;
* `WP_Error`;
* non-2xx;
* malformed JSON;
* API errors.

Do not pass secrets into errors or to the frontend.

Check the current official Jotform REST API documentation for authentication and
the form list before implementing. Do not guess endpoints.

### Forms cache

Add fetching and caching of the Jotform forms list.

Admin actions:

* Test Connection
* Refresh Forms

Do not call Jotform on every admin page view when the cached list is still
current. Do not call Jotform on frontend page requests.

### Admin feedback

Show comprehensible states:

* Not configured
* Connected
* Connection failed

And for the forms:

* loaded;
* unavailable;
* needs refresh.

## Security

Use:

* the `manage_options` capability;
* an admin nonce for actions;
* sanitization;
* contextual escaping.

Never print the API key into HTML, JS or logs.

## Verification

After implementing:

1. Activate the plugin through the WordPress Playground MCP server.
2. Check that there are no fatal errors.
3. Check that the admin menu and settings appear.
4. Open the Settings page through the Playwright MCP server.
5. Check the UI states.
6. If the Jotform connection is safely available, run a read-only Test
   Connection and Refresh Forms.
7. If a live connection is unavailable, say so plainly and exercise the error
   handling through a safe fixture, a mock, or an invalid configuration.

The Jotform MCP server may be used for a read-only comparison of the forms list
where it is available.

Do not modify Jotform forms.
