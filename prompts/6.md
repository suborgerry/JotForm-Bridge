# STAGE 6 — Security, Performance, Reliability and Release Readiness

> **Historical.** This stage is finished. The file records what was asked for at
> the time, not what the code does now — some of it has since been overturned by
> the `Amendment:` sections in `AGENTS.md`. Read it for the reasoning, not as an
> instruction, and never as a description of current behaviour.

Read `AGENTS.md`.

Do NOT add large new product features in this stage. The goal is to check and
harden the MVP that already exists.

Work as a security and reliability reviewer of the existing system.

---

## 1. Security audit

Review the whole plugin for:

* missing capability checks;
* missing nonces;
* insufficient sanitization;
* insufficient escaping;
* path traversal;
* arbitrary file inclusion;
* user-controlled include;
* API key exposure;
* debug information exposure;
* unsafe REST input;
* unexpected arrays and objects;
* an oversized payload;
* unrestricted options;
* integration slug manipulation.

Fix whatever this turns up.

---

## 2. Secret audit

Confirm the Jotform API key cannot reach:

* frontend HTML;
* inline JS;
* frontend JS localization;
* a REST response;
* logs;
* exception messages;
* an admin HTML value attribute after saving;
* the browser network payload.

Check the authorization headers too.

---

## 3. Template security

Confirm the renderer accepts a TemplateRegistry entry and nothing else. No:

* `../`;
* arbitrary absolute paths;
* REST-provided paths;
* query parameter paths.

Template discovery must not execute PHP.

---

## 4. REST hardening

Check:

* method restrictions;
* malformed JSON;
* an unknown Integration;
* a disabled Integration;
* an invalid schema;
* unknown fields;
* unexpected nesting;
* arrays where scalars are expected;
* scalars where arrays are expected;
* request size;
* an upstream timeout;
* the behaviour of a repeated request.

Failures have to be safe, with no technical leak.

---

## 5. Cache audit

Check the caching of:

* the account forms;
* the Jotform schema;
* the normalized schema;
* the TemplateRegistry.

An ordinary frontend request must not call the Jotform API where the data it
needs is cached. A page with no form on it must not call Jotform at all.
TemplateScanner must not run on every frontend request.

---

## 6. Cache invalidation

Check:

* Refresh Forms;
* Refresh Schema;
* Rescan Templates;
* an Integration update;
* a theme switch;
* a plugin version upgrade, where relevant.

Do not leave obviously stale references behind after a template or schema
changes.

---

## 7. External API failure

Check the behaviour on:

* a DNS or network failure;
* a timeout;
* 401/403;
* 404;
* 429;
* 500+;
* a malformed Jotform response.

The admin gets a useful diagnostic; the frontend gets a safe generic error.
Never report success silently.

---

## 8. Logging

Debug logging is disabled by default. Check the redaction.

Logs must not contain:

* the API key;
* an auth header;
* the full sensitive form payload;
* password-like field data.

Log the minimum technical metadata needed.

---

## 9. The spam protection extension point

Building a Turnstile integration now is not required. But confirm a clean
extension point exists immediately before the upstream submission, for example:

`jotform_bridge_spam_check`

A failing spam check has to stop the request, and the architecture has to allow
Cloudflare Turnstile to be added later without rewriting the REST controller.

---

## 10. WordPress compatibility

Check the minimum:

WordPress 6.4+

PHP 8.0+

Find and remove any PHP 8.1+ syntax or features in use. Do not use a WordPress
API introduced after 6.4 without a fallback.

---

## 11. Lifecycle

Activation:

* no fatal error;
* minimal setup.

Deactivation:

* do not delete user configuration.

Uninstall:

* do not delete persistent configuration unexpectedly.

Where the cleanup policy is not explicitly defined, it is better not to destroy
Integrations or settings automatically.

---

## 12. Internationalization

Prepare every plugin-owned UI string for translation through the standard
WordPress mechanisms.

Do not try to translate:

* Jotform labels;
* developer template HTML;

where those come from an external schema or template.

---

## 13. Assets

Confirm:

* the frontend JS does not depend on jQuery;
* the user needs no build step;
* the production assets are ready as shipped;
* assets are not enqueued globally without a need.

---

## 14. Performance

Check that there are:

* no N+1 Jotform calls;
* no Jotform calls on an ordinary frontend request;
* no filesystem scanning on every page load;
* no repeated normalization without a need;
* no admin list that calls the API once per row.

---

## 15. Full regression tests

Run the whole suite. Add regression tests for the bugs found.

Particular attention to:

* FieldNormalizer;
* collisions;
* the fingerprint;
* TemplateScanner;
* TemplateValidator;
* SubmissionValidator;
* SubmissionMapper;
* the REST controller;
* API errors;
* both renderers.

---

## 16. MCP regression

WordPress Playground:

* activation;
* settings;
* Integration CRUD;
* schema refresh;
* template rescan;
* the helper;
* the shortcode;
* the custom renderer;
* the auto renderer;
* REST.

Playwright:

the full custom flow;

the full auto flow;

the admin flow;

the validation and error flow;

Where a development Jotform form exists, perform at least one full test
submission and verify it through the Jotform MCP server. Do not use a production

## 18. The release ZIP

The plugin has to be ready to package as an ordinary ZIP:

Plugins
→ Add New
→ Upload Plugin
→ Activate

After installation, none of these may be required:

`composer install`

`npm install`

`npm run build`

If Composer is used for autoloading, the production files it needs have to be in
the package.

---

## 19. Final architecture review

Finally, confirm no violations of the key invariants have crept in:

* a template does not know the Jotform Form ID;
* a template does not know a qid;
* the Integration is the binding layer;
* the Normalized Schema is the only schema contract;
* custom and auto share one submission pipeline;
* JotformClient is the centralized API layer;
* the API key is server-only;
* the TemplateRegistry is an allowlist;
* backend validation is authoritative.
