
======================================================================
ЭТАП 6 — Security, Performance, Reliability и Release Readiness
===============================================================

Прочитай `AGENTS.md`.

На этом этапе НЕ добавляй крупные новые product features.

Цель — проверить и укрепить уже реализованный MVP.

Работай как security/reliability reviewer существующей системы.

---

# 1. Security Audit

Проверь весь plugin на:

* missing capability checks;
* missing nonces;
* insufficient sanitization;
* insufficient escaping;
* path traversal;
* arbitrary file inclusion;
* user-controlled include;
* API key exposure;
* debug information exposure;
* unsafe REST input;
* unexpected arrays/objects;
* oversized payload;
* unrestricted options;
* integration slug manipulation.

Исправь найденные проблемы.

---

# 2. Secret Audit

Убедись, что Jotform API key не может попасть:

* frontend HTML;
* inline JS;
* frontend JS localization;
* REST response;
* logs;
* exception messages;
* admin HTML value attribute после сохранения;
* browser network payload.

Проверь также authorization headers.

---

# 3. Template Security

Убедись, что renderer принимает только TemplateRegistry entry.

Никаких:

* `../`;
* arbitrary absolute paths;
* REST-provided paths;
* query parameter paths.

Template discovery не должна execute PHP.

---

# 4. REST Hardening

Проверить:

* method restrictions;
* malformed JSON;
* unknown Integration;
* disabled Integration;
* invalid schema;
* unknown fields;
* unexpected nesting;
* arrays вместо scalars;
* scalars вместо arrays;
* request size;
* upstream timeout;
* repeated request behavior.

Safe failures без technical leak.

---

# 5. Cache Audit

Проверь caching:

* account forms;
* Jotform schema;
* normalized schema;
* TemplateRegistry.

Обычный frontend request не должен обращаться к Jotform API, если необходимые data cached.

Страница без формы вообще не должна вызывать Jotform.

TemplateScanner не должен запускаться каждый frontend request.

---

# 6. Cache Invalidation

Проверить:

* Refresh Forms;
* Refresh Schema;
* Rescan Templates;
* Integration update;
* theme switch;
* plugin version upgrade, если relevant.

Не оставлять очевидно stale references после изменения template/schema.

---

# 7. External API Failure

Проверь поведение при:

* DNS/network failure;
* timeout;
* 401/403;
* 404;
* 429;
* 500+;
* malformed Jotform response.

Admin должен получить useful diagnostic.

Frontend — safe generic error.

Не silently report success.

---

# 8. Logging

Debug logging disabled default.

Проверь redaction.

Логи не должны содержать:

* API key;
* auth header;
* полный sensitive form payload;
* password-like field data.

Логировать минимально необходимую technical metadata.

---

# 9. Spam Protection Extension

Не обязательно сейчас создавать Turnstile integration.

Но убедись, что существует clean extension point непосредственно до upstream submission.

Например:

`jotform_bridge_spam_check`

Failure spam check должен остановить request.

Архитектура должна позволять позже подключить Cloudflare Turnstile без переписывания REST Controller.

---

# 10. WordPress Compatibility

Проверь minimum:

WordPress 6.4+

PHP 8.0+

Найди и убери PHP 8.1+ syntax/features, если они используются.

Не использовать WordPress API, появившийся после 6.4, без fallback.

---

# 11. Lifecycle

Activation:

* no fatal;
* minimal setup.

Deactivation:

* не удалять user configuration.

Uninstall:

не удалять persistent configuration неожиданно.

Если cleanup policy явно не определена — лучше не уничтожать Integration/settings автоматически.

---

# 12. Internationalization

Все plugin-owned UI strings подготовить к translation стандартными WordPress mechanisms.

Не пытайся переводить:

* Jotform labels;
* developer template HTML;

если они приходят из внешней schema/template.

---

# 13. Assets

Убедись:

* frontend JS не зависит от jQuery;
* build step не нужен пользователю;
* production assets уже готовы;
* assets не подключаются глобально без необходимости.

---

# 14. Performance

Проверь:

* нет N+1 Jotform calls;
* нет Jotform calls на обычном frontend request;
* нет filesystem scanning каждый page load;
* нет повторной normalization без необходимости;
* Admin lists не вызывают API для каждой строки.

---

# 15. Full Regression Tests

Запусти полный test suite.

Добавь regression tests на найденные bugs.

Особое внимание:

* FieldNormalizer;
* collision;
* fingerprint;
* TemplateScanner;
* TemplateValidator;
* SubmissionValidator;
* SubmissionMapper;
* REST Controller;
* API errors;
* both renderers.

---

# 16. MCP Regression

WordPress Playground:

* activation;
* settings;
* Integration CRUD;
* schema refresh;
* template rescan;
* helper;
* shortcode;
* Custom renderer;
* Auto renderer;
* REST.

Playwright:

полный Custom flow.

полный Auto flow.

Admin flow.

Validation/error flow.

Double submit.

Если есть development Jotform form:

выполнить минимум один полный test submission и проверить Jotform MCP.

Не использовать production form.

---

# 18. Release ZIP

Plugin должен быть готов к упаковке как обычный ZIP:

Plugins
→ Add New
→ Upload Plugin
→ Activate

После установки НЕ должны требоваться:

`composer install`

`npm install`

`npm run build`

Если Composer используется для autoload, необходимые production files должны входить в package.

---

# 19. Final Architecture Review

В конце проверь, что не появились нарушения ключевых invariants:

* Template не знает Jotform Form ID.
* Template не знает qid.
* Integration является binding layer.
* Normalized Schema — единственный schema contract.
* Custom и Auto используют один submission pipeline.
* JotformClient — centralized API layer.
* API key server-only.
* TemplateRegistry — allowlist.
* Backend validation authoritative.
