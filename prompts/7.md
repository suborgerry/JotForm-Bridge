# STAGE 7 — Success Redirect (per Integration)

> **Historical.** This stage is finished. The file records what was asked for at
> the time, not what the code does now — some of it has since been overturned by
> the `Amendment:` sections in `AGENTS.md`. Read it for the reasoning, not as an
> instruction, and never as a description of current behaviour.

Read `AGENTS.md`, and the `Success redirect` section in particular.

The goal of the stage is to make it possible to redirect after a successful
submission to a page chosen separately for each form (Integration).

Do not add other product features in this stage.

---

## 1. The data model

Extend Integration:

```text
success_action    message | redirect
redirect_page_id  int, a WordPress page/post ID
redirect_delay    int, seconds, 0 by default
```

Requirements:

* the default is `message`;
* existing stored integrations keep working with no migration;
* absent keys are read as the defaults;
* sanitize on save;
* validate before use;
* `redirect_delay` is capped at a sensible maximum.

Do not create new database tables.

---

## 2. Admin UI

On the Integration form, add:

* `Success Action` — a choice of `message` / `redirect`;
* `Redirect Page` — a choice among existing published pages/posts;
* `Redirect Delay` — a number of seconds.

The page is chosen from a controlled list (`wp_dropdown_pages()` or equivalent),
not a free-text URL input.

`Redirect Page` and `Redirect Delay` are shown only when
`Success Action = redirect`.

On the integrations list and on the Integration screen, show
`Redirect target status` alongside the existing `Schema status` and
`Template compatibility`.

The status has to say plainly when the chosen page is:

* deleted;
* in the trash;
* not published.

---

## 3. Backend resolution

The redirect URL is resolved by the backend at the moment the success response
is built.

Never store the URL itself in the Integration — only the page ID is stored.

Checks before handing out a URL:

* the page exists;
* the page is published;
* the URL is internal to the site (`wp_validate_redirect()`, or a host check
  against `home_url()`).

If a check fails:

* no redirect is issued;
* the submission still counts as successful;
* the behaviour degrades to the ordinary success message;
* the fact is recorded in the debug log, where logging is on.

A successful submission must never fail because of a broken redirect target.

---

## 4. The REST response

A success response with a redirect configured:

```json
{
    "success": true,
    "message": "Form submitted successfully.",
    "redirect": {
        "url": "https://example.com/thanks/",
        "delay": 0
    }
}
```

The `redirect` key is absent where no redirect is configured or the target is
invalid.

The frontend does not send a redirect URL in the submission request, and any
redirect-related input in the request is ignored.

A validation failure and an upstream error never carry `redirect`.

---

## 5. Frontend JavaScript

Update `assets/frontend.js`.

The order in which a success is handled:

1. set the form's success state;
2. write the success message into its slot;
3. dispatch `jotformbridge:success`;
4. perform the redirect.

Requirements:

* the `detail` of `jotformbridge:success` carries `redirect`;
* the event is cancelable as far as the redirect is concerned: `preventDefault()`
  cancels the navigation;
* the redirect uses `window.location.assign()`;
* with `delay > 0`, it waits;
* the form stays disabled for the duration of the delay;
* a second submit after a successful one is impossible;
* the absence of `redirect` in the response changes nothing about current
  behaviour.

Do not put submission data in the query string.

---

## 6. Both renderers

The redirect works identically for the custom template and for AutoRenderer.

A template knows nothing about the redirect: it is an Integration-level setting,
not part of the template contract.

Do not introduce new `data-jotform-*` attributes for the redirect.

---

## 7. Security

Check:

* an open redirect is impossible;
* an external host is rejected;
* a protocol-relative URL (`//evil.example`) is rejected;
* the redirect URL never comes from the request;
* the redirect page ID is validated when the URL is handed out, independently of
  any capability;
* saving the settings is protected by a capability check and a nonce;
* no submission values appear in the URL.

---

## 8. Caching

The redirect URL is resolved per submission request and is not cached alongside
the schema.

A changed page permalink has to show up in the very next response.

Updating an Integration must not invalidate the schema cache without a need.

---

## 9. Tests

Add tests for:

* the defaults for an integration with no redirect fields;
* sanitizing and validating the new fields;
* a success response without a redirect;
* a success response with a redirect;
* a deleted page → no redirect, the success is preserved;
* a draft or trashed page → no redirect;
* an external URL is rejected;
* redirect fields in the request are ignored;
* a validation failure carries no redirect;
* an upstream error carries no redirect;
* delay clamping.

Run the whole suite and the linter.

## 10. MCP verification

WordPress Playground:

* create an Integration with `Success Action = redirect`;
* choose a page;
* save and re-read the settings;
* check the status after the chosen page is deleted.

Playwright:

* the custom flow with a redirect;
* the auto flow with a redirect;
* a redirect with a delay;
* cancelling the redirect through `preventDefault()`;
* a validation error — no redirect happens;
* a double submit during the delay.
