# ЭТАП 7 — Success Redirect (per-Integration)

Прочитай `AGENTS.md`, особенно раздел `Success redirect`.

Цель этапа — дать возможность настроить redirect после успешного submission на
страницу, выбираемую отдельно для каждой формы (Integration).

Не добавляй других product features в этом этапе.

---

## 1. Модель данных

Расширить Integration:

```text
success_action    message | redirect
redirect_page_id  int, WordPress page/post ID
redirect_delay    int, секунды, 0 по умолчанию
```

Требования:

* значение по умолчанию — `message`;
* существующие сохраненные integrations продолжают работать без миграции;
* отсутствующие ключи трактуются как defaults;
* sanitize при сохранении;
* validate перед использованием;
* `redirect_delay` ограничен разумным максимумом.

Не создавать новые database tables.

---

## 2. Admin UI

На форме Integration добавить:

* `Success Action` — выбор `message` / `redirect`;
* `Redirect Page` — выбор существующей published page/post;
* `Redirect Delay` — число секунд.

Выбор страницы — контролируемый список (`wp_dropdown_pages()` или эквивалент),
не свободный текстовый URL input.

Поля `Redirect Page` и `Redirect Delay` отображаются только при
`Success Action = redirect`.

В списке integrations и на странице Integration показывать
`Redirect target status` рядом с существующими `Schema status` и
`Template compatibility`.

Статус должен явно сообщать о проблеме, если выбранная страница:

* удалена;
* в trash;
* не published.

---

## 3. Backend resolution

Redirect URL резолвится backend в момент формирования success response.

Никогда не сохранять сам URL в Integration — сохраняется только page ID.

Проверки перед выдачей URL:

* page существует;
* page published;
* URL внутренний для сайта (`wp_validate_redirect()` или проверка host против
  `home_url()`).

Если проверка не проходит:

* redirect не выдается;
* submission все равно считается успешным;
* поведение деградирует до обычного success message;
* факт фиксируется в debug log (при включенном logging).

Успешная отправка никогда не должна падать из-за сломанного redirect target.

---

## 4. REST response

Success response при настроенном redirect:

```json
{
    "success": true,
    "message": "Form submitted successfully.",
    "redirect": {
        "url": "https://example.com/thanks/",
        "delay": 0
    }
}
```

Ключ `redirect` отсутствует, если redirect не настроен или target невалиден.

Frontend не передает redirect URL в submission request.

Любой redirect-related input из request игнорируется.

Validation failure и upstream error никогда не содержат `redirect`.

---

## 5. Frontend JavaScript

Обновить `assets/frontend.js`.

Порядок обработки success:

1. установить success state формы;
2. записать success message в соответствующий слот;
3. dispatch `jotformbridge:success`;
4. выполнить redirect.

Требования:

* `detail` события `jotformbridge:success` содержит `redirect`;
* событие cancelable в части redirect: `preventDefault()` отменяет переход;
* redirect через `window.location.assign()`;
* при `delay > 0` — переход после задержки;
* форма остается disabled в течение задержки;
* повторный submit после успешной отправки невозможен;
* отсутствие `redirect` в ответе не меняет текущее поведение.

Не добавлять submission data в query string.

---

## 6. Оба renderer

Redirect работает одинаково для Custom Template и AutoRenderer.

Template не должен ничего знать о redirect: это Integration-level настройка,
а не template contract.

Не вводить новых `data-jotform-*` атрибутов для redirect.

---

## 7. Security

Проверить:

* open redirect невозможен;
* внешний host отклоняется;
* protocol-relative URL (`//evil.example`) отклоняется;
* redirect URL не берется из request;
* redirect page ID проходит capability-независимую валидацию на выдаче;
* сохранение настроек защищено capability check и nonce;
* никаких submission values в URL.

---

## 8. Caching

Redirect URL резолвится на запрос submission и не кэшируется вместе со schema.

Изменение permalink страницы должно немедленно отражаться в новом ответе.

Обновление Integration не должно инвалидировать schema cache без необходимости.

---

## 9. Tests

Добавить тесты:

* defaults для integration без redirect-полей;
* sanitize/validate новых полей;
* success response без redirect;
* success response с redirect;
* удаленная page → нет redirect, success сохраняется;
* draft/trashed page → нет redirect;
* внешний URL отклоняется;
* redirect-поля в request игнорируются;
* validation failure не содержит redirect;
* upstream error не содержит redirect;
* delay clamping.

Запустить полный test suite и lint.
