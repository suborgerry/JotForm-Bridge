# ЭТАП 3 — Integrations, Custom Templates и Template Validation

Прочитай `AGENTS.md`.

Перед изменениями изучи существующую реализацию этапов 1 и 2.

Normalized Schema является уже существующим внутренним контрактом.

Не создавай вторую альтернативную schema representation.

На этом этапе НЕ реализовывай:

* frontend JavaScript;
* public REST submission;
* отправку submissions в Jotform;
* SubmissionMapper;
* AutoRenderer.

Цель этапа:

Jotform Form
+
Integration
+
Custom PHP Template
+
Schema Compatibility

---

## 1. Integration

Создай domain/repository слой для Integration.

Integration содержит минимум:

* name;
* slug;
* Jotform Form ID;
* rendering mode;
* template slug;
* active status.

Rendering modes:

`custom`

`auto`

На этом этапе `auto` можно сохранять как configuration, но AutoRenderer пока не реализовывать.

Slug должен:

* быть sanitized;
* быть уникальным;
* использоваться как public local identifier.

Например:

`contact`

В theme code никогда не должен требоваться Jotform Form ID.

---

## 2. Integration storage

Использовать WordPress options.

Не создавать custom DB table.

Repository должен отвечать за:

* list;
* get by slug;
* create;
* update;
* delete;
* uniqueness validation.

Не размещать прямые `get_option/update_option` по всему plugin.

## 5. Custom Template directory

Основной путь:

`/forms/`

в активной theme.

Например:

`wp-content/themes/example/forms/contact.php`

Учитывать:

* child theme;
* parent theme.

Child theme имеет priority.

Добавить filter:

`jotform_bridge_template_paths`

для дополнительных directories.

Не поддерживать Sage/Blade.

Только PHP templates.

---

## 6. Template Metadata

Template определяется по header:

```php
<?php
/*
Jotform Template Name: Contact Form
Jotform Template Slug: contact
*/
```

Обязательные значения:

* Jotform Template Name
* Jotform Template Slug

Нельзя использовать:

`Jotform Form ID`

в template metadata.

Template должен быть полностью независим от конкретной Jotform Form.

---

## 7. TemplateScanner

Создай `TemplateScanner`.

Он должен:

* получить разрешенные paths;
* безопасно найти PHP files;
* прочитать только необходимую часть source;
* получить header metadata;
* не execute PHP;
* reject invalid metadata;
* обнаруживать duplicate slugs;
* учитывать child theme priority;
* предотвращать directory traversal;
* возвращать diagnostics.

Не scanning filesystem на каждом page request.

---

## 8. TemplateRegistry

Результат discovery кешировать.

Entry примерно:

```php
[
    'slug' => 'contact',
    'name' => 'Contact Form',
    'file' => '/trusted/theme/path/forms/contact.php',
]
```

Runtime renderer позднее сможет использовать только registered entry.

Arbitrary filepath использовать запрещено.

---

## 9. Rescan Templates

Добавь admin action:

`Rescan Templates`

Она должна:

* invalidate registry;
* повторно scan;
* сохранить registry;
* показать результат.

Например:

`3 templates found`

или diagnostics duplicate/invalid header.

---

## 10. Template Field Discovery

Для compatibility validation извлекай из source literal значения:

`data-jotform-field="..."`

Например:

`email`

`name.first`

`name.last`

Не execute template.

Не пытайся вычислить динамический PHP:

```php
data-jotform-field="<?php echo $something; ?>"
```

Если field identifier динамический, static validator не должен угадывать его.

Можно показать warning:

`Dynamic field identifier cannot be statically validated.`

---

## 11. TemplateValidator

Создай отдельный validator:

Template fields
vs
Normalized Schema

Определять:

* matched;
* required schema field missing;
* optional schema field missing;
* template field unknown;
* unsupported required schema field;
* unsupported optional schema field;
* dynamic/unverifiable field.

Статусы:

`Compatible`

`Compatible with warnings`

`Invalid`

Правила:

Required field missing → Invalid.

Unknown template field → Invalid.

Optional schema field missing → Warning.

Unsupported required field → Invalid или explicit blocking diagnostic.

---

## 12. Composite Validation

Validator должен корректно работать с paths:

`name.first`

`name.last`

`address.city`

и т. д.

Не считать наличие `name` достаточным, если template реально должен содержать конкретные required children.

Используй structure Normalized Schema.

---

## 13. Schema Refresh

На Integration edit screen добавь:

`Refresh Schema`

При нажатии:

1. получить current Jotform schema;
2. normalize;
3. сохранить новую cached schema;
4. вычислить fingerprint;
5. повторно выполнить TemplateValidator;
6. обновить compatibility state.

Покажи administrator, изменилась ли schema.

## 17. MCP Verification

WordPress Playground:

1. Используй test theme.
2. Создай `/forms/contact.php`.
3. Выполни Rescan Templates.
4. Проверь registry.
5. Создай Integration.
6. Привяжи cached/test Jotform schema.

Playwright:

1. Открой Integrations.
2. Создай Integration через UI.
3. Выбери Jotform Form.
4. Выбери Custom Template.
5. Проверь compatibility.
6. Намеренно удали required `data-jotform-field` из test template.
7. Rescan/Refresh.
8. Убедись, что status становится `Invalid`.

На этом этапе Jotform submission НЕ выполнять.

## Acceptance Criteria

Этап завершен, когда:

* integrations CRUD работает;
* form выбирается через select;
* template discovery работает;
* `/forms/` поддерживается;
* child theme priority работает;
* template registry кешируется;
* Rescan Templates работает;
* template fields statically обнаруживаются;
* schema/template validator работает;
* diagnostics отображаются;
* Refresh Schema обновляет compatibility.

В конце покажи:

* структуру хранения Integration;
* структуру TemplateRegistry;
* пример valid template;
* пример invalid compatibility report;
* tests;
* MCP verification.

Не переходи к Этапу 4 самостоятельно.
