# STAGE 2 — Jotform Schema Engine and FieldNormalizer

> **Historical.** This stage is finished. The file records what was asked for at
> the time, not what the code does now — some of it has since been overturned by
> the `Amendment:` sections in `AGENTS.md`. Read it for the reasoning, not as an
> instruction, and never as a description of current behaviour.

Read `AGENTS.md` at the project root and treat it as the primary architectural
specification.

Study the stage 1 code carefully before changing anything. Do not rewrite
working architecture without an objective need.

Do NOT implement in this stage:

* custom templates;
* TemplateScanner;
* the Integrations UI;
* frontend forms;
* frontend JavaScript;
* REST submission;
* SubmissionMapper;
* AutoRenderer.

The goal of this stage is a dependable internal Schema Engine that converts a
Jotform-specific schema into a stable Normalized Schema of our own.

---

## 1. Fetching Jotform questions

Extend the existing `JotformClient` with only what is needed to fetch the
questions/schema of one Jotform Form.

Check the current official Jotform REST API documentation first. Do not guess:

* the endpoint;
* authentication;
* the response format;
* the structure of a question;
* how composite fields are represented.

Use the handling that already exists:

* `WP_Error`;
* timeouts;
* non-2xx;
* malformed JSON;
* upstream API errors.

Do not duplicate the HTTP logic.

---

## 2. The Normalized Schema

Create an internal representation of a Jotform form schema, independent of both
the frontend and the Jotform API response format.

It becomes the main internal contract for the stages that follow:

Jotform Questions
↓
FieldNormalizer
↓
Normalized Schema
↓
Templates / Rendering / Validation / SubmissionMapper

Each normalized field carries at least:

* the semantic key;
* the raw Jotform qid;
* the original machine-readable Jotform name;
* the label;
* the normalized type;
* required;
* options, where applicable;
* children/subfields, where applicable;
* supported / unsupported status;
* whatever metadata later submission mapping needs.

Value objects, classes or arrays are all acceptable — pick the simplest
maintainable option. Do not build a domain framework nobody asked for.

---

## 3. Semantic keys

The frontend will later address fields through semantic identifiers:

`email`

`message`

`name.first`

`name.last`

`address.city`

The raw qid is used inside the backend only. A qid must never become a public
semantic identifier.

Use the most stable machine-readable field Jotform provides. Do not rely on the
visible label alone: a label may change, repeat, contain spaces, contain
punctuation, or be localized.

Semantic key generation has to be:

* deterministic;
* predictable;
* testable.

If two Jotform fields produce the same semantic key: do not guess. Record the
collision as a schema diagnostic or error. The raw qid remains the authoritative
identifier inside the backend.

---

## 4. FieldNormalizer

Implement a separate `FieldNormalizer`, responsible for:

Jotform question
→ normalized field

Do not put that logic in:

* JotformClient;
* the admin UI;
* a future renderer;
* the REST controller.

Support at least the following types, where their structure is confirmed against
the current Jotform API:

* textbox/text;
* textarea;
* email;
* phone;
* full name;
* address;
* dropdown/select;
* radio;
* checkbox;
* number.

Support date only where the actual API representation is understood and can be
implemented correctly. Do not make assumptions just to tick a box.

---

## 5. Composite fields

This is the critical part. Check the real Jotform schema for composite fields.

The normalized structure has to make this possible later:

`name.first`

`name.last`

along with the other parts of Full Name that genuinely exist.

For Address:

`address.street`

`address.city`

`address.state`

`address.zip`

or the real semantic child names that match the Jotform API.

Do not invent child names where the API uses different ones. Normalize them into
a stable internal contract, and keep everything needed to reverse the conversion
at submission time.

---

## 6. Options

For:

* dropdown;
* radio;
* checkbox;

the Normalized Schema has to carry the list of permitted options where the
Jotform API provides them. Server-side validation will need it later.

Do not keep options as a bare string where they can safely be turned into a
structured representation.

---

## 7. Unsupported fields

Where a Jotform field type is not supported yet, do not silently turn it into a
textbox. Use an explicit state:

`supported = false`

or equivalent, and keep:

* the qid;
* the label;
* the original Jotform type;
* a diagnostic reason.

Such a field has to be visible to the layers above and to the administrator. A
required unsupported field matters most, because it will later have to block
AutoRenderer or mark the Integration as problematic.

---

## 8. FormSchema

Create a suitable abstraction for the whole Normalized Schema. It has to allow:

* getting a field by semantic key;
* determining the required fields;
* getting the supported and unsupported fields;
* getting the flattened semantic paths;
* getting the diagnostics;
* detecting collisions.

Do not over-complicate the API.

---

## 9. Schema fingerprint

Implement a deterministic schema fingerprint/hash. It has to change when the
schema changes meaningfully:

* a field added or removed;
* a qid changed;
* required status changed;
* a field type changed;
* relevant children changed;
* options changed.

Do not include random or runtime metadata in the fingerprint.

The fingerprint is what later answers:

`Jotform schema changed`

---

## 10. Schema cache

Add a cache per Jotform Form ID, so that using a schema does not mean an API
request every time. Provide:

* get cached schema;
* force refresh;
* cache invalidation.

Use standard WordPress mechanisms. Do not create a separate database table.

> Superseded: the schema is no longer a cache. See "Amendment: manual schema
> synchronization" in `AGENTS.md`.

---

## 11. Tests

This is one of the most test-heavy stages of the project.

Add fixtures that look as much as possible like real, sanitized Jotform API
responses. Unit tests must not reach a live Jotform.

Test at least:

* textbox;
* textarea;
* email;
* phone;
* full name;
* address;
* select;
* radio;
* checkbox;
* number;
* required=false;
* required=true;
* semantic key normalization;
* collisions;
* unsupported fields;
* options normalization;
* composite children;
* the schema fingerprint;
* fingerprint stability;
* the fingerprint changing after a schema modification.

Where the structure of some type is unknown, check the official documentation or
a real read-only schema first, rather than inventing a fixture.

---

## 12. Read-only live verification

Where a Jotform test or development form is available, fetch its schema
read-only through the Jotform REST API.

The Jotform MCP server may be used to inspect an existing test form, but it does
not replace the REST API documentation.

Do not modify a Jotform Form. Do not create a submission.

If a real test schema cannot be obtained safely, use fixtures and say so.

---

## 13. WordPress Playground verification

Through the WordPress Playground MCP server:

* activate the updated plugin;
* confirm there are no fatal errors;
* check the schema cache;
* check a forced refresh;
* check the services inside the WordPress runtime.

Do not move on to the browser frontend — there is no frontend at this stage.

---

## Acceptance criteria

The stage is finished when:

1. JotformClient can fetch the questions of a given form.
2. Questions are converted into a Normalized Schema.
3. The raw qid is kept as backend metadata only.
4. Semantic fields do not depend on the qid.
5. Composite fields have stable child paths.
6. Options are structured.
7. Unsupported fields are identified explicitly.
8. Collisions are detected.
9. The schema has a deterministic fingerprint.
10. The schema is cached.
11. A forced refresh works.
12. The critical normalization logic is covered by tests.
13. The plugin still activates without errors.

Afterwards, show an example Normalized Schema, and list:

* which Jotform field types are supported;
* which are unsupported;
* which composite child identifiers are used;
* which API assumptions were confirmed against the documentation;
* which MCP verifications were run;
* what was left unverified.

Do not move on to stage 3 on your own.
