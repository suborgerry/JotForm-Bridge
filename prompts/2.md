# ЭТАП 2 — Jotform Schema Engine и FieldNormalizer

Прочитай `AGENTS.md` в корне проекта и считай его основной архитектурной спецификацией.

Перед изменениями внимательно изучи уже реализованный код Этапа 1.

Не переписывай работающую архитектуру без объективной необходимости.

На этом этапе НЕ реализовывай:

* custom templates;
* TemplateScanner;
* Integrations UI;
* frontend forms;
* frontend JavaScript;
* REST submission;
* SubmissionMapper;
* AutoRenderer.

Цель этого этапа — построить надежный внутренний Schema Engine, который преобразует Jotform-specific schema в стабильную Normalized Schema нашего приложения.

---

## 1. Получение Jotform Questions

Расширь существующий `JotformClient` только необходимой функциональностью для получения questions/schema конкретной Jotform Form.

Перед реализацией обязательно проверь актуальную официальную Jotform REST API documentation.

Не угадывай:

* endpoint;
* authentication;
* response format;
* structure question;
* representation composite fields.

Используй уже существующую обработку:

* `WP_Error`;
* timeout;
* non-2xx;
* malformed JSON;
* upstream API errors.

Не дублируй HTTP logic.

---

# 2. Normalized Schema

Создай внутреннее представление Jotform form schema.

Normalized Schema должна быть независима от frontend и Jotform API response format.

Она будет основным внутренним контрактом для следующих этапов:

Jotform Questions
↓
FieldNormalizer
↓
Normalized Schema
↓
Templates / Rendering / Validation / SubmissionMapper

Каждое normalized field должно содержать минимум:

* semantic key;
* raw Jotform qid;
* original/machine-readable Jotform name;
* label;
* normalized type;
* required;
* options, если применимо;
* children/subfields, если применимо;
* supported / unsupported status;
* необходимые metadata для последующего submission mapping.

Можно использовать value objects/classes или массивы — выбери наиболее простое maintainable решение.

Не создавай лишнюю domain framework.

---

# 3. Semantic Keys

Frontend в будущем должен обращаться к полям через semantic identifiers.

Например:

`email`

`message`

`name.first`

`name.last`

`address.city`

Raw qid использовать только внутри backend.

Нельзя превращать qid в public semantic identifier.

Используй наиболее стабильное machine-readable поле, которое предоставляет Jotform.

Не полагайся исключительно на visible label.

Label может:

* измениться;
* повторяться;
* содержать пробелы;
* содержать punctuation;
* быть локализован.

Semantic key generation должна быть:

* deterministic;
* predictable;
* testable.

Если два Jotform fields получают одинаковый semantic key:

не угадывай.

Зафиксируй collision как schema diagnostic/error.

Raw qid при этом остается authoritative identifier внутри backend.

---

# 4. FieldNormalizer

Реализуй отдельный `FieldNormalizer`.

Его ответственность:

Jotform question
→ normalized field

Не размещай эту логику:

* в JotformClient;
* Admin UI;
* будущих Renderer;
* REST Controller.

Поддержи минимум следующие типы, если их структура подтверждена актуальным Jotform API:

* textbox/text;
* textarea;
* email;
* phone;
* full name;
* address;
* dropdown/select;
* radio;
* checkbox;
* number.

Date поддерживай только если actual API representation понятна и может быть реализована корректно.

Не делай предположений только ради галочки.

---

# 5. Composite Fields

Это критичная часть.

Проверь реальную Jotform schema для composite fields.

Нормализованная структура должна позволять в будущем использовать:

`name.first`

`name.last`

и другие реально существующие части Full Name.

Для Address:

`address.street`

`address.city`

`address.state`

`address.zip`

или реальные semantic child names, которые соответствуют Jotform API.

Не придумывай child names, если API использует другие.

Нормализуй их в стабильный internal contract.

Храни всю информацию, необходимую для обратного преобразования при submission.

---

# 6. Options

Для:

* dropdown;
* radio;
* checkbox;

Normalized Schema должна содержать список допустимых options, если Jotform API предоставляет их.

Это позже потребуется для server-side validation.

Не хранить options только как строку, если их можно безопасно преобразовать в структурированное представление.

---

# 7. Unsupported Fields

Если тип Jotform field пока не поддержан:

не превращай его молча в textbox.

Используй explicit состояние:

`supported = false`

или аналогичное.

Сохрани:

* qid;
* label;
* original Jotform type;
* diagnostic reason.

Такой field должен быть виден последующим слоям и Administrator.

Required unsupported field особенно важен, потому что позже он должен блокировать AutoRenderer или помечать Integration как problematic.

---

# 8. FormSchema

Создай подходящую abstraction для целой Normalized Schema.

Она должна позволять:

* получить field по semantic key;
* определить required fields;
* получить supported/unsupported fields;
* получить flattened semantic paths;
* получить diagnostics;
* обнаружить collisions.

Не переусложняй API.

---

# 9. Schema Fingerprint

Реализуй deterministic schema fingerprint/hash.

Fingerprint должен меняться при значимых изменениях schema, например:

* добавлено/удалено field;
* изменился qid;
* изменился required status;
* изменился field type;
* изменились relevant children;
* изменились options.

Не включай в fingerprint случайные/runtime metadata.

Fingerprint нужен для последующего определения:

`Jotform schema changed`

---

# 10. Schema Cache

Добавь cache per Jotform Form ID.

Не выполнять API request при каждом использовании schema.

Предусмотри:

* get cached schema;
* force refresh;
* cache invalidation.

Используй стандартные WordPress mechanisms.

Не создавай отдельную database table.

---

# 11. Tests

Это один из наиболее важных test-heavy этапов проекта.

Добавь fixtures, максимально похожие на реальные sanitized Jotform API responses.

Unit tests не должны обращаться к live Jotform.

Обязательно протестируй:

* textbox;
* textarea;
* email;
* phone;
* full name;
* address;
* select;
* radio;
* checkbox;
* number;
* required=false;
* required=true;
* semantic key normalization;
* collision;
* unsupported field;
* options normalization;
* composite children;
* schema fingerprint;
* fingerprint stability;
* fingerprint change после schema modification.

Если структура какого-либо типа неизвестна — сначала проверь официальную документацию/real read-only schema, а не создавай выдуманный fixture.

---

# 12. Read-only live verification

Если доступен Jotform test/development form:

получи schema read-only через Jotform REST API.

Можно использовать Jotform MCP для inspection существующей test form, но MCP не заменяет REST API documentation.

Не изменяй Jotform Form.

Не создавай submission.

Если реальную test schema получить безопасно нельзя — используй fixtures и сообщи об этом.

---

# 13. WordPress Playground Verification

Через WordPress Playground MCP:

* активируй обновленный plugin;
* убедись в отсутствии fatal errors;
* проверь schema cache;
* проверь forced refresh;
* проверь работу services внутри WordPress runtime.

Не переходи к browser frontend, потому что frontend на этом этапе еще нет.

---

# Acceptance Criteria

Этап завершен, когда:

1. JotformClient может получить questions конкретной form.
2. Questions преобразуются в Normalized Schema.
3. Raw qid хранится только как backend metadata.
4. Semantic fields не зависят от qid.
5. Composite fields имеют стабильные child paths.
6. Options структурированы.
7. Unsupported fields определяются явно.
8. Collisions обнаруживаются.
9. Schema имеет deterministic fingerprint.
10. Schema кешируется.
11. Force refresh работает.
12. Critical normalization logic покрыта tests.
13. Plugin по-прежнему активируется без ошибок.

После завершения покажи пример Normalized Schema.

Также перечисли:

* какие Jotform field types поддерживаются;
* какие unsupported;
* какие composite child identifiers используются;
* какие API assumptions подтверждены документацией;
* какие MCP verification были выполнены;
* что осталось непроверенным.

Не переходи к Этапу 3 самостоятельно.
